# Спецификация: Event Management

## Задача

Человеку нужно место, где он объявляет о своём событии — встрече, митапе, лекции — и где другие
люди на это событие записываются. Сегодня это делается в переписке: организатор пишет пост,
желающие отвечают «+», организатор вручную считает и никому ничего не подтверждает. Запись
теряется, дубли не видны, а тот, кто записался, не получает ничего, что можно показать на входе.

Отдельная часть задачи — предъявить работу как инженерную: это тестовое задание на позицию
Full-Stack Python Developer. Значит, важно не только что оно работает, но и что видно, **как**
оно сделано: проверяемые решения, стандартные механизмы фреймворка и отсутствие лишнего.

## Решение

REST API на Django + DRF и маленький React-клиент к нему.

Любой посетитель видит список событий, ищет по нему и фильтрует. Зарегистрированный
пользователь создаёт свои события, правит и удаляет только их, записывается на чужие и
отменяет свою запись. После записи ему уходит письмо с названием, датой и местом — отправляется
фоном, HTTP-ответ его не ждёт. Повторно записаться нельзя ни через интерфейс, ни в обход его —
это запрещено ограничением в базе, а не только проверкой в коде.

Весь стек поднимается одной командой `docker compose up --build`: backend, postgres, redis,
celery-worker и фронтенд за nginx. API документирован через OpenAPI 3.1, Swagger UI открыт на
`/api/docs/`.

## Решения по реализации

### §1. Стек и версии

Стек взят из брифа целиком. Правило версий — одно и на все пакеты: **каждая зависимость
закрепляется по минорной версии, ни одна — по патчу** (`Django>=5.2,<5.3`,
`djangorestframework>=3.16,<3.17`, и так далее для всех строк `requirements*.txt` и всех
зависимостей `package.json`, где используется `^`). Так патчи безопасности приезжают сами, а
мажорное обновление не приезжает внезапно. Бриф просит именно это: «current stable, mutually
compatible package versions rather than hardcoding patch versions» (R44). Конкретные минорные
версии выбираются на момент сборки — актуальные стабильные, совместимые между собой.

| Слой | Что | Зачем именно это |
|---|---|---|
| Python | 3.12+ | R25 |
| Backend | Django 5.x, DRF | R26, R27 |
| БД | PostgreSQL 16 | R28; SQLite запрещён явно |
| Аутентификация | djangorestframework-simplejwt (+ `token_blacklist`) | R29, R66 |
| Фильтры | django-filter | R30 |
| Документация | drf-spectacular | R31 |
| Очередь | Celery + Redis | R32, R33 |
| Статика | whitenoise | единственное добавление к списку брифа: gunicorn не отдаёт статику, а без неё ломается вёрстка Django-admin и не отдаётся `/static/`. Одна зависимость с конкретной задачей — это условие §4 брифа, а не нарушение |
| Сервер | gunicorn | `runserver` — не для сдачи «production-oriented» |
| Тесты | pytest, pytest-django | R34 |
| Качество | ruff, pre-commit | R35, R36 |

**Чего нет и почему:** factory_boy (фикстур pytest достаточно), pytest-mock (`unittest.mock`
входит в стандартную библиотеку), django-cors-headers (фронтенд и API — один origin, см. §13),
django-environ (`os.environ` + небольшой хелпер закрывает всё, что нужно). Каждое из них —
зависимость без задачи, а §65 брифа требует обратного.

### §2. Структура репозитория

Дерево из §5 брифа, с двумя отступлениями, оба — потому что буквальное следование дереву
сломало бы то, ради чего дерево нарисовано:

- **`pyproject.toml` лежит в `backend/`, а не в корне.** Он конфигурирует ruff и pytest, которые
  запускаются внутри контейнера backend, где корня репозитория нет. Файл в корне не был бы виден
  той команде, которая его читает.
- **Зависимости — в `backend/requirements.txt` и `backend/requirements-dev.txt`.** Django-проект
  не является устанавливаемым пакетом; `pip install .` потребовал бы придумать фиктивный пакет
  ради формы. Бриф сам разрешает: «If a file is not needed, do not create it just to follow the
  tree literally» (R48).

`config/middleware.py` и `config/exceptions.py` создаются — в них есть содержание (§11).
`apps/events/services.py` **не создаётся**: у CRUD нет бизнес-логики, и §24 брифа это прямо
запрещает.

### §3. Модель данных

```python
class User(AbstractUser):
    email = EmailField(unique=True)          # USERNAME_FIELD
    username = CharField(max_length=150, unique=True)   # отображаемое имя
    USERNAME_FIELD = "email"
    REQUIRED_FIELDS = ["username"]

class Event(Model):
    title = CharField(max_length=200)
    description = TextField()
    date = DateTimeField(db_index=True)
    location = CharField(max_length=200, db_index=True)
    organizer = ForeignKey(User, on_delete=CASCADE, related_name="organized_events")
    created_at = DateTimeField(auto_now_add=True)
    updated_at = DateTimeField(auto_now=True)

    class Meta:
        ordering = ["date", "id"]

class EventRegistration(Model):
    event = ForeignKey(Event, on_delete=CASCADE, related_name="registrations")
    user = ForeignKey(User, on_delete=CASCADE, related_name="registrations")
    created_at = DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [UniqueConstraint(fields=["user", "event"], name="uniq_user_event")]
```

Почему так:

- **Кастомная модель пользователя с первой миграции** (R49) — позже её не заменить без боли.
  `USERNAME_FIELD = "email"` — решение брифинга (G01); `username` остаётся, потому что пример
  ответа API в §56 брифа показывает организатора именно по `username`.
- **Обычные автоинкрементные ключи** — R55, UUID не вводим.
- **`ordering = ["date", "id"]`** — детерминированный порядок, без которого пагинация
  перемешивает строки между страницами.
- **`on_delete=CASCADE` у записей** — soft delete запрещён (R56); удалённое событие уносит свои
  записи, и это единственное честное поведение без истории.
- **Индексы ровно на `date` и `location`** — только те два поля, по которым бриф требует
  фильтрацию и сортировку (R96). Индекса на `title` нет: поиск по нему идёт через `icontains`,
  и B-tree там всё равно не работает — притворяться оптимизацией не будем.

### §4. Аутентификация: JWT в HttpOnly-cookie

SimpleJWT из коробки читает токен из заголовка `Authorization`. Бриф требует cookie (R63, R64),
поэтому:

| Единица | Что делает |
|---|---|
| `CookieJWTAuthentication(JWTAuthentication)` | берёт access-токен из cookie `access_token`, а не из заголовка; при успешной аутентификации выполняет CSRF-проверку (§5) |
| `set_auth_cookies(response, access, refresh)` | ставит обе cookie с одинаковыми флагами |
| `clear_auth_cookies(response)` | удаляет обе |

Параметры cookie:

```text
access_token   HttpOnly, SameSite=Lax, Secure=$COOKIE_SECURE, Path=/api/,          Max-Age=ACCESS_LIFETIME
refresh_token  HttpOnly, SameSite=Lax, Secure=$COOKIE_SECURE, Path=/api/v1/auth/,  Max-Age=REFRESH_LIFETIME
```

- **`SameSite=Lax`, а не `None`** — фронтенд и API отдаются с одного origin через nginx (§13).
  `None` потребовал бы `Secure` даже на localhost и открыл бы cookie для кросс-сайтовых запросов
  без необходимости.
- **`Secure` — из переменной окружения**, `False` в dev по HTTP, `True` в production (R71).
  В README сказано прямо: `COOKIE_SECURE=True` обязателен при реальном деплое.
- **Разные `Path`** — refresh-cookie не уезжает с каждым запросом к API, только на два эндпоинта,
  которым он нужен. Это уменьшает поверхность, ничего не стоит и не требует кода.
- **Время жизни** (R67): access — 10 минут, refresh — 7 дней, оба из env.
- **Ротация:** `ROTATE_REFRESH_TOKENS=True`, `BLACKLIST_AFTER_ROTATION=True`. Каждый refresh
  выдаёт новую пару и гасит предыдущий refresh — украденный токен живёт до первого честного
  обновления.

Эндпоинты:

| Метод и путь | Тело запроса | Ответ |
|---|---|---|
| `POST /api/v1/auth/register/` | `email, username, password` | 201, `{id, email, username}`. Cookie **не ставит**: регистрация и вход — разные операции, фронтенд после 201 вызывает вход |
| `POST /api/v1/auth/token/` | `email, password` | 200, `{"user": {...}}` + обе cookie. Токенов в теле нет — иначе их можно было бы положить в `localStorage`, что R65 запрещает |
| `POST /api/v1/auth/token/refresh/` | — (refresh из cookie) | 200 `{"detail": "Token refreshed."}` + новые cookie |
| `POST /api/v1/auth/logout/` | — | 204, refresh в blacklist, обе cookie удалены |
| `GET /api/v1/auth/me/` | — | 200 `{id, email, username}` / 401 |
| `GET /api/v1/auth/csrf/` | — | 204 + `csrftoken` cookie |

Выход по уже стухшему или отсутствующему refresh — тоже 204: выход не должен уметь падать
(история 12).

### §5. CSRF

Раз аутентификация живёт в cookie, браузер отправляет её сам — значит, нужна защита от CSRF
(R70), и отключать её нельзя.

Механика: `CookieJWTAuthentication` после успешной проверки токена вызывает
`rest_framework.authentication.CSRFCheck` ровно так, как это делает штатная `SessionAuthentication`.
Провал → 403. Это не самодельная защита, а штатный механизм Django, включённый явно.

- `csrftoken` — **не** HttpOnly: его читает JavaScript и кладёт в заголовок `X-CSRFToken`.
  Это и есть схема double-submit, на которой построен Django.
- Axios настроен `xsrfCookieName: "csrftoken"`, `xsrfHeaderName: "X-CSRFToken"`,
  `withCredentials: true` — заголовок проставляется сам.
- `GET /api/v1/auth/csrf/` (`@ensure_csrf_cookie`) вызывается при старте приложения, чтобы cookie
  существовала до первого POST — в том числе до входа, когда пользователь ещё аноним.
- Настройки, полностью: `django.middleware.csrf.CsrfViewMiddleware` включён (он стоит в
  `MIDDLEWARE` и не удаляется ни в каком окружении), `CSRF_COOKIE_HTTPONLY = False` — иначе
  JS не прочитает токен и схема не работает, `CSRF_COOKIE_SAMESITE = "Lax"`,
  `CSRF_COOKIE_SECURE = COOKIE_SECURE`, `CSRF_TRUSTED_ORIGINS` — список из env (R111).
- **CORS не настраивается вообще, и это осознанно.** В docker-схеме браузер видит один origin
  (§12). В локальной разработке без Docker фронтенд запускается `npm run dev`, а Vite проксирует
  `/api` на `http://localhost:8000` — снова один origin. Кросс-доменного сценария в проекте нет,
  поэтому django-cors-headers не появляется. `CORS_ALLOWED_ORIGINS` остаётся в `.env.example`,
  потому что его называет бриф, и в README сказано, что настройка вступит в силу только если
  фронтенд начнут отдавать с другого домена — тогда понадобится и пакет, и `SameSite=None`.
- Безопасные методы (`GET`, `HEAD`, `OPTIONS`) проверку не проходят и не должны.

### §6. Контракты API

Формат ответов — штатный DRF, без конверта (R87). Версия — в пути: `/api/v1/` (R57).

**События** (`EventViewSet`, `ModelViewSet`, R82):

```text
GET    /api/v1/events/          публично, пагинация + фильтры + поиск + сортировка
POST   /api/v1/events/          аутентифицированные
GET    /api/v1/events/{id}/     публично
PATCH  /api/v1/events/{id}/     только организатор
DELETE /api/v1/events/{id}/     только организатор
```

`PUT` не включается: бриф перечисляет только `PATCH` (R73), а частичное обновление закрывает
все сценарии фронтенда. `http_method_names` ограничен явно, чтобы `PUT` отдавал 405, а не
работал по умолчанию.

Сериализаторы (R86):

- `EventWriteSerializer` — `title, description, date, location`. Поля `organizer` нет вообще:
  подделать его нечем (история 18). `organizer` подставляется в `perform_create`.
- `EventSerializer` (чтение) — `id, title, description, date, location, organizer{id, username},
  registrations_count, is_registered, created_at, updated_at`.

`registrations_count` и `is_registered` — аннотации queryset, не свойства модели: иначе список из
десяти событий даёт двадцать лишних запросов (R95).

```python
Event.objects.select_related("organizer").annotate(
    registrations_count=Count("registrations"),
    is_registered=Exists(EventRegistration.objects.filter(event=OuterRef("pk"), user=request.user)),
)
```

Для анонима `is_registered` — константа `False`, без подзапроса.

**D01 (обнаружено в таске 03).** Эта аннотация не резолвится до появления модели
`EventRegistration` — Django не регистрирует обратную связь `registrations` заранее. Таск 03
корректно вернул `BLOCKED` вместо самодельной модели-заглушки. Фактический порядок: таск 03
строит `EventSerializer` без этих двух полей, таск 04 (где `EventRegistration` появляется)
дописывает их в `apps/events/serializers.py` и `apps/events/views.py` задним числом, вместе с
регрессионным тестом в `apps/events/tests/`. Требование то же (R154i), меняется только то, какой
таск его закрывает.

**Про `prefetch_related` (§29 брифа).** Он здесь не нужен, и это решение, а не пропуск: ни один
ответ API не сериализует коллекцию связанных объектов — количество записей приходит аннотацией,
а поимённого списка записавшихся в объёме нет («Вне рамок»). `prefetch_related` появится ровно
в тот день, когда появится этот список; ставить его сейчас — это то самое «mechanically add these
methods everywhere», которое бриф запрещает в том же параграфе.

**Записи** (R74, R88):

```text
POST   /api/v1/events/{id}/register/    201 | 400 | 401 | 404 | 409
DELETE /api/v1/events/{id}/register/    204 | 401 | 404
```

Оба — `@action(detail=True, methods=["post", "delete"], url_path="register")` на
`EventViewSet`. Отдельного административного API регистраций нет (R88).

**Permissions** (R76–R81):

| Действие | Класс |
|---|---|
| `list`, `retrieve` | `AllowAny` |
| `create` | `IsAuthenticated` |
| `update`, `destroy` | `IsAuthenticated` + `IsOrganizerOrReadOnly` (объектный уровень) |
| `register` | `IsAuthenticated` |

Каждое правило проверяется тестом, который бьёт по HTTP напрямую (история 26).

### §7. Ошибки и коды

| Ситуация | Код | Тело |
|---|---|---|
| создано событие / запись | 201 | объект |
| удалено, выход | 204 | пусто |
| невалидное поле | 400 | `{"field": ["message"]}` |
| нет аутентификации | 401 | `{"detail": …}` |
| нет прав / CSRF | 403 | `{"detail": …}` |
| нет объекта, нет записи | 404 | `{"detail": …}` |
| повторная запись | 409 | `{"detail": "You are already registered for this event."}` |
| неожиданная ошибка | 500 | `{"detail": "Internal server error.", "request_id": …}` |

409 делается классом `AlreadyRegistered(APIException)` с `status_code = 409` — DRF не имеет
готового исключения для конфликта, а руками собранный `Response` в сервисе смешал бы слои.

### §8. Фильтры, поиск, сортировка, пагинация

```python
class EventFilter(FilterSet):
    location = CharFilter(lookup_expr="icontains")
    date_after = DateTimeFilter(field_name="date", lookup_expr="gte")
    date_before = DateTimeFilter(field_name="date", lookup_expr="lte")
    organizer = NumberFilter(field_name="organizer_id")
    registered = BooleanFilter(method="filter_registered")   # только для аутентифицированного
```

`organizer` и `registered` — то, чем наполняется `/my-events` (история 61): вкладка «что
организую» это `?organizer=<мой id>`, вкладка «куда записан» — `?registered=true`. Отдельного
эндпоинта под страницу не заводим: это тот же список событий с другим фильтром, и `?registered`
для анонима просто ничего не меняет. Без этих двух фильтров страница не наполнялась бы ничем.

- `location` — `icontains`, а не точное совпадение: `?location=kyiv` должен находить «Kyiv».
- `search` — `SearchFilter` по `title, description, location` (R91).
- `ordering` — `OrderingFilter`, разрешены `date`, `created_at`, `title`; по умолчанию `date`.
- Пагинация — `PageNumberPagination`, `page_size = 10`, параметр `page_size` до 100 (R94).

Elasticsearch не вводится (R93), кэш Redis не вводится (R110).

### §9. Асинхронная почта

```text
POST /events/{id}/register/
   → сервис: проверка правил, создание записи внутри transaction.atomic
   → transaction.on_commit(lambda: send_registration_email.delay(user.id, event.id))
   → HTTP 201
```

- Задача принимает **два int** (R107). Модели в очередь не уезжают — их состояние к моменту
  выполнения уже другое, а сериализация модели в брокер лишь маскирует это.
- Постановка — строго в `on_commit` (R108): иначе воркер может прочитать запись до коммита или
  отправить письмо об откатившейся записи.
- `task_ignore_result = True`: результат никому не нужен, и Redis не становится ещё и хранилищем
  результатов (R110).
- Celery Beat не подключается (R109).
- Письмо: тема `You are registered for {title}`, тело — название, дата, место, подтверждение
  (R106). Шаблон — обычный текст, без HTML: HTML-письмо здесь ничего не добавляет.

### §10. Логирование и обработка исключений

- **`RequestLogMiddleware`** (R103): на каждый запрос — одна строка
  `method=POST path=/api/v1/events/ status=201 duration_ms=34 request_id=… user_id=…`.
  `request_id` берётся из `X-Request-ID`, если он пришёл, иначе генерируется; возвращается в
  ответе тем же заголовком.
- **`custom_exception_handler`** (R101): вызывает штатный DRF-обработчик; если тот вернул `None`
  — это не-DRF исключение: пишем `logger.exception` с `request_id` и отдаём 500 без внутренних
  деталей. Если вернул ответ — **не трогаем его вообще**: тело остаётся стандартным DRF, потому
  что R87 запрещает менять формат ответов. Связь с логом даёт заголовок `X-Request-ID`, который
  middleware ставит на любой ответ, включая ошибочные. Конвертов вида `{"success": true, "data": …}`
  нет (R101, R87).
- `logging` настраивается в `settings.py`, вывод в stdout, `print()` в коде нет (R102).

### §11. Конфигурация

Все переменные из §43 брифа, плюс `COOKIE_SECURE`, `ACCESS_TOKEN_LIFETIME_MINUTES`,
`REFRESH_TOKEN_LIFETIME_DAYS`, `DJANGO_LOG_LEVEL`, `DEMO_USER_PASSWORD`. Читаются в

`.env.example` содержит **все** имена с безопасными значениями для локального запуска и пустыми

### §12. Docker и запуск

Пять сервисов, ровно как в §61 брифа, backend называется `backend` везде (R136):

| Сервис | Что |
|---|---|
| `postgres` | postgres:16-alpine, healthcheck `pg_isready`, том для данных |
| `redis` | redis:7-alpine, healthcheck `redis-cli ping` |
| `backend` | entrypoint: ждёт postgres → `migrate` → gunicorn на 8000 |
| `celery-worker` | тот же образ, `celery -A config worker -l info` |
| `frontend` | multi-stage: node собирает, nginx отдаёт статику и проксирует `/api/`, `/admin/`, `/static/` на `backend:8000`; порт 3000 |

Два следствия этой схемы, ради которых она и выбрана (R151i):

- **Один origin.** Браузер видит и приложение, и API на `http://localhost:3000`. Поэтому
  `SameSite=Lax` достаточно, CORS не нужен вовсе, и django-cors-headers не появляется в
  зависимостях. `CORS_ALLOWED_ORIGINS` остаётся в `.env.example` как имя (бриф его называет), но
  в текущей схеме не используется — об этом сказано в README прямо, чтобы никто не искал
  несуществующую настройку.
- **Миграции применяются при старте**, потому что R135 требует рабочий стек от одной команды.
  Развести два пути так, чтобы они не спорили: entrypoint выполняет **только `migrate`** и
  никогда `makemigrations`. Файлы миграций пишет разработчик руками
  (`docker compose exec backend python manage.py makemigrations`) и коммитит их в репозиторий —
  ровно как требует §62 брифа. Контейнер применяет то, что уже лежит в репозитории, и не
  генерирует ничего сам: сгенерированная на старте миграция не попала бы в git и разъехалась бы
  между машинами.

### §13. Тесты

`pytest` + `pytest-django`, конфигурация в `backend/pyproject.toml`. Пункты §60 брифа
(R128–R133) разложены в конкретные случаи — это и есть список тестов, который должен
существовать:

**Аутентификация** (`apps/users/tests/`): регистрация успешна → 201 и пользователь в базе ·
регистрация с занятым email → 400 · регистрация со слабым паролем → 400 · пароля нет ни в одном
ответе · вход по верной паре → 200 и обе cookie в ответе · вход по неверной паре → 401 · refresh
по cookie → 200 и новая пара · refresh без cookie → 401 · logout → 204, cookie удалены, повторный
refresh тем же токеном → 401 (blacklist) · logout без cookie → 204 · `/me/` аутентифицированному
→ 200, анониму → 401 · небезопасный запрос без `X-CSRFToken` → 403.

**События** (`apps/events/tests/`): список анониму → 200 · создание анониму → 401 · создание
аутентифицированному → 201 и `organizer` = текущий пользователь · `organizer` в теле запроса
игнорируется · дата в прошлом → 400 · retrieve → 200 · retrieve несуществующего → 404 · PATCH
своего → 200 · PATCH чужого → 403 · DELETE своего → 204 · DELETE чужого → 403 · `PUT` → 405 ·
поиск по слову из title / description / location · фильтр `location` регистронезависимо ·
`date_after` / `date_before` · `ordering=date` и `ordering=-date` · пагинация: вторая страница,
`count`, стабильный порядок · `registered=true` и `organizer=<id>` · число запросов на списке
константно (`django_assert_num_queries`).

**Записи** (`apps/registrations/tests/`): запись → 201 · повторная запись → 409 · запись анониму
→ 401 · запись на прошедшее событие → 400 · отмена → 204 · отмена без записи → 404 · чужая запись
недостижима · дубль в обход сервиса → `IntegrityError` · после успешной записи `.delay` вызван с
двумя int · при откате транзакции `.delay` не вызван · `registrations_count` и `is_registered`
меняются после записи и после отмены.

Группы соответствуют модулям; файлы лежат в `tests/` каждого приложения.

Приёмы, которыми проверяется то, что иначе проверить нельзя:

- **`on_commit`** — фикстурой `django_capture_on_commit_callbacks`.
- **Постановка задачи** — `unittest.mock.patch` на `.delay`, проверяются аргументы: два int.
- **Ограничение базы** — создание дубля в обход сервиса, ожидается `IntegrityError`.
- **N+1** — `django_assert_num_queries` на списке из нескольких событий.

Фронтенд-тестов нет: бриф их не требует, а тестовый фреймворк ради одного смоук-теста — это
зависимость без задачи. Проверка фронтенда — `npm run type-check` и сборка (они и ловят реальные
классы ошибок TypeScript-проекта). Это записано в «Вне рамок».

### §14. Фронтенд

Структура — из §5 брифа. Маршрутизация — **React Router** (R38): `createBrowserRouter`,
маршруты `/login`, `/register`, `/events`, `/events/:id`, `/events/create`, `/events/:id/edit`,
`/my-events`, плюс `*` → страница «не найдено». Ключевые решения:

- **`api/client.ts`** — один axios-инстанс: `baseURL=/api/v1`, `withCredentials: true`,
  настройки XSRF, интерсептор ответа. На 401 (кроме самого `/auth/token/refresh/`): один
  общий refresh на всю очередь ожидающих запросов, затем повтор исходных; при неудаче —
  `queryClient.clear()` и переход на `/login` (истории 8–10).
- **Состояние аутентификации** — запрос `useMe()` к `/auth/me/`. Никакого глобального стора:
  TanStack Query и есть кэш (R122).
- **Формы** — React Hook Form + Zod через `zodResolver`; ошибки полей с сервера раскладываются в
  `setError`, форма при ошибке не очищается.
- **Компоненты** — `Navbar`, `Button`, `Input`, `Textarea`, `EventCard`, `EventForm`,
  `Pagination`, `LoadingState`, `ErrorState`, `EmptyState`, `ConfirmDialog`. `ConfirmDialog` — это
  и есть `Modal` из списка §47 брифа: единственное модальное окно в проекте — подтверждение
  удаления события, и абстрактный `Modal` без второго применения был бы абстракцией без задачи.
  Больше компонентов не вводим (R121, R120).
- **Tailwind** — единственная стилизация; адаптив через `sm:`/`md:`/`lg:` (R23, R119).
- **Поиск** — debounce 300 мс, состояние поиска и фильтров живёт в query-параметрах URL: ссылку
  на отфильтрованный список можно переслать, и кнопка «назад» работает как ожидается.
- **Локальная разработка без Docker** (§62 брифа): `npm install`, затем `npm run dev` — Vite на
  5173 с `server.proxy` для `/api` на `http://localhost:8000`. Прокси нужен не для удобства:
  без него фронтенд и API оказываются на разных origin, и cookie перестают ходить. Проверка
  типов — `npm run type-check`, сборка — `npm run build`.

### §15. Качество, документация, демо-данные

- ruff (lint + format) и pre-commit на `ruff check --fix` и `ruff format` (R35, R36).
- Комментарии — минимум, только английский; каждый комментарий объясняет «почему», а не «что»
  (R140). Кандидаты на комментарий в этом проекте ровно три: CSRF-проверка внутри
  аутентификации, `on_commit` перед постановкой задачи, и `Path` у refresh-cookie.
- Аннотации типов там, где они улучшают схему и читаемость (R141).
- `seed_demo` — management command: два пользователя (пароль из `DEMO_USER_PASSWORD`,
  по умолчанию `demo12345`) и 15 событий в разных городах и датах, часть уже с записями
  (G04). Идемпотентна: повторный запуск не плодит дубли.
- README на английском по структуре §63 брифа; каждая команда перед сдачей выполняется.
  Два раздела, которые иначе окажутся пустой формальностью, определяются здесь:
  **Architecture Decisions** — почему JWT в HttpOnly-cookie, а не в `localStorage`; почему
  ограничение уникальности в базе, а не только проверка в коде; почему письмо ставится в
  `on_commit`; почему сервис есть у записей и нет у CRUD; почему один origin вместо CORS; почему
  нет UUID и soft delete. **Future Improvements** — поимённый список записавшихся для
  организатора, лимит мест на событие, тесты фронтенда, CI. Каждый пункт — две-три строки, без
  общих слов.

### §16. Порядок сборки

Порядок из §68 брифа (R146) — он и задаёт последовательность тасков в плане. Здесь он записан
потому, что это требование заказчика, а не деталь планирования: каждый следующий шаг опирается
на предыдущий, и перестановка ломает не стиль, а работу.

| Фаза брифа | Что готово в конце |
|---|---|
| 1. Project setup | Django + DRF + PostgreSQL, конфигурация из env, Docker поднимается |
| 2. Users/Auth | модель пользователя, регистрация, JWT в cookie, refresh, blacklist, logout, `/me`, CSRF |
| 3. Events | модель, сериализаторы, ViewSet, права, CRUD |
| 4. Registrations | модель, ограничение уникальности, запись/отмена, сервис, транзакции |
| 5. Filtering | django-filter, поиск, сортировка, пагинация |
| 6. Async email | Redis, Celery, задача письма, постановка после коммита |
| 7. API documentation | drf-spectacular, OpenAPI, Swagger UI, ReDoc |
| 8. Tests | весь список §13 |
| 9. Frontend | React, TypeScript, Vite, Tailwind, роутинг, вход, список, карточка, формы, запись |
| 10. Final polish | ruff, pre-commit, README, проверка Docker и документации, адаптив, чистка зависимостей и комментариев, финальный прогон тестов |

Фазы 1–8 — это бэкенд, и он идёт первым целиком: фронтенд не к чему прикручивать, пока API не
отвечает. Фазы 3 и 4 можно вести параллельно только после того, как готова фаза 2, — обе
опираются на модель пользователя.

### §17. Чеклист сдачи

Чеклист §70 брифа (R145) — это и есть список приёмки: 47 пунктов, каждый проверяется на живом

### §18. Решения сверх брифа и их родители

Всё, чего в брифе нет, а в сборке будет. Каждая строка называет требование, которому она служит:
решения без родителя в этом проекте не остаётся ни одного.

| Решение | Родитель | Почему без него не выходит |
|---|---|---|
| nginx отдаёт фронтенд и проксирует API | R134, R135, R151i | фронтенд надо чем-то отдавать в контейнере; один origin снимает CORS и делает cookie рабочими |
| gunicorn вместо `runserver` | R147 | «production-oriented implementation» — `runserver` в сдаче выглядит как незаконченность |
| whitenoise | R147 | gunicorn не отдаёт статику, без неё ломается Django-admin |
| `requirements*.txt`, `pyproject.toml` в `backend/` | R48 | конфигурация должна быть видна команде, которая её читает (§2) |
| healthcheck'и postgres и redis | R135 | без них backend стартует раньше базы, и «одна команда» не работает |
| `migrate` в entrypoint | R135 | то же самое: пустая база после `up` — это не поднятый стек |
| `GET /api/v1/auth/csrf/` | R70 | CSRF-cookie нужна до первого POST, в том числе до входа |
| ротация refresh + blacklist после ротации | R66 | blacklist только на logout оставляет украденный refresh живым до истечения |
| разные `Path` у access- и refresh-cookie | R63, R64 | refresh незачем ездить с каждым запросом |
| `registrations_count`, `is_registered` в ответе | R154i, R117 | без них фронтенд не знает, какую кнопку показать, и не может показать заполненность |
| запрет даты в прошлом при создании; запрет записи на прошедшее | R98 (G02) | «valid event dates» из §32 брифа иначе не означает ничего |
| тело `POST /auth/token/` = `{"user": …}`, регистрация без cookie | R65 | токены в теле — приглашение положить их в `localStorage` |
| `http_method_names` без `PUT` | R73 | бриф перечисляет `PATCH`; молча работающий `PUT` — незадокументированное поведение |
| `?page_size=` с потолком 100 | R94 | без потолка параметр превращается в способ выгрузить всю базу |
| `Event.objects.with_stats(user)` | R95 | одно место, где собирается запрос списка, вместо копии аннотаций во вьюхе |
| фильтры `organizer` и `registered` | R116 | `/my-events` нечем наполнить |
| заголовок `X-Request-ID` | R103 | correlation ID из §41 брифа без него не связывается с жалобой пользователя |
| ретраи и `task_ignore_result` у Celery | R107, R110 | §37 брифа разрешает ретраи «where genuinely useful»; временный отказ SMTP — ровно этот случай |
| `EMAIL_BACKEND=console` по умолчанию | R148i, R18 | иначе бонусное требование невозможно увидеть без почтового сервера |
| `COOKIE_SECURE`, `*_LIFETIME_*`, `DJANGO_LOG_LEVEL`, `DEMO_USER_PASSWORD` | R111 | §43 брифа называет список «Potential variables»; эти четыре нужны решениям §4 и §15 |
| `seed_demo` | R153i | пустой список не показывает ни пагинацию, ни фильтры |
| single-flight refresh, `queryClient.clear()` при провале | R68 | «transparently» без очереди даёт пять параллельных refresh и гонку |
| debounce и фильтры в URL | R91, R117 | запрос на каждое нажатие клавиши и непересылаемая ссылка |
| `ordering = ["date", "id"]` | R94 | без детерминированного порядка пагинация перемешивает строки |
| `Textarea`, `ConfirmDialog` | R121 | `description` — многострочное поле; удаление без подтверждения теряет данные |

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `apps.users` | моделью `User`, регистрацией, входом, выходом, `/me`, всей cookie-механикой JWT | `User`, `UserSerializer`, `CookieJWTAuthentication`, `set_auth_cookies(response, access, refresh)`, `clear_auth_cookies(response)` | имена и флаги cookie, blacklist, порядок CSRF-проверки |
| `apps.events` | моделью `Event`, CRUD-API, фильтрами, правами на событие | `Event`, `EventSerializer`, `EventWriteSerializer`, `IsOrganizerOrReadOnly`, `EventFilter`, `Event.objects.with_stats(user)` | аннотации, устройство queryset, детали фильтров |
| `apps.registrations` | моделью `EventRegistration`, правилами записи и отмены, письмом | `EventRegistration`, `register_user_for_event(user, event) -> EventRegistration`, `cancel_registration(user, event) -> None`, `send_registration_email(user_id, event_id)` | обработку дубля, `transaction.on_commit`, содержимое письма, политику ретраев |
| `config` | настройками, корневым роутингом, сквозным поведением | `custom_exception_handler`, `RequestLogMiddleware`, `celery_app` | формат лога, генерацию `request_id` |
| `frontend/src/api` | транспортом к API | `api` (axios-инстанс) | интерсепторы, очередь refresh, XSRF |
| `frontend/src/features/*` | доступом к своему куску API и типами | `useEvents`, `useEvent`, `useCreateEvent`, `useUpdateEvent`, `useDeleteEvent`, `useRegister`, `useCancelRegistration`, `useMe`, `useLogin`, `useRegisterUser`, `useLogout` | ключи кэша, инвалидацию, формы URL |

Зависимости идут в одну сторону: `registrations` → `events` → `users`. Обратных импортов нет;
`events` ничего не знает о записях, кроме аннотации по `related_name`.

**Шов для тестов — один: HTTP API через `rest_framework.test.APIClient`.** Всё поведение
бэкенда проверяется снаружи, через те же URL, которыми пользуется фронтенд. Два исключения,
и они названы явно, потому что через HTTP их проверить нельзя:

1. `apps.registrations.services` — тест гонки и тест `on_commit`.
2. ORM напрямую — тест ограничения уникальности в базе.
