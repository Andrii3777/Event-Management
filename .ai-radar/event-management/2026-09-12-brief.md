# Event Management — Final Implementation Specification

> **Handoff document for the implementation agent**
>
> Implement the project according to the specification below. The goal is to produce a clean, production-oriented Django REST API with a small React/TypeScript frontend, while avoiding unnecessary architecture and dependencies.
>
> When a choice is not explicitly specified here, prefer standard Django/DRF conventions and the simplest maintainable solution.

---

# 1. Original Task

Build a **Django REST API for Event Management**.

The application should allow users to:

- create events;
- view events;
- update events;
- delete events;
- register users for events.

The original task explicitly requires:

- Event model;
- Event CRUD;
- basic user registration and authentication;
- event registration;
- API documentation;
- Docker;
- README.

Bonus:

- event search/filtering;
- email notifications after event registration.

All mandatory requirements and both bonus requirements should be implemented.

# 6. Django Architecture

Use Django's natural architecture.

Django apps should represent features:

```text
apps/users
apps/events
apps/registrations
```

This is conceptually similar to feature modules in NestJS.

Do **not** attempt to recreate NestJS's:

```text
*.module.ts
*.dto.ts
*.entity.ts
```

structure in Django.

Use Django/DRF conventions instead.

# 7. Database

Use:

**PostgreSQL**

Do not use SQLite for the final implementation.

PostgreSQL is appropriate because:

- it is explicitly relevant to the target vacancy;
- it is a production-oriented relational database;
- Django ORM works naturally with it;
- database constraints and indexes can be used properly.

# 8. User Model

Use Django authentication.

A custom user model is preferred if it can be implemented cleanly from the beginning.

At minimum, support:

```text
id
email or username
password
```

Passwords must use Django's password hashing.

Never expose passwords through API responses.

# 9. Event Model

Conceptually:

```text
Event
-----
id
title
description
date
location
organizer → User
created_at
updated_at
```

Required fields from the original task are mandatory:

```text
title
description
date
location
organizer
```

The organizer must be derived from the authenticated user.

For example:

```text
POST /api/v1/events/

request.user
     ↓
event.organizer
```

Do not allow clients to create events on behalf of another user by submitting an arbitrary organizer ID.

---

# 10. Event Registration Model

Use a separate relationship model:

```text
EventRegistration
-----------------
id
event → Event
user → User
created_at
```

Add a database-level uniqueness constraint:

```text
unique(user, event)
```

This is important because application-level duplicate checks alone are not sufficient under concurrent requests.

---

# 11. UUIDs

Do not introduce UUIDs unless there is a concrete reason.

Normal Django primary keys are sufficient for this task.

UUIDs are not required simply because they are sometimes considered a best practice.

# 12. Soft Delete

There is no requirement for:

- audit history;
- recovery;
- legal retention;
- deleted-object reporting.

Normal `DELETE` is sufficient.

# 15. JWT Storage

Final decision:

### Access token

Store in:

**HttpOnly + Secure cookie**

### Refresh token

Store in:

**HttpOnly + Secure cookie**

Therefore:

```text
Browser
├── access_token  → HttpOnly cookie
└── refresh_token → HttpOnly cookie
```

Frontend JavaScript must not directly read the JWTs.

Do not use `localStorage` or `sessionStorage` for authentication tokens.

---

# 16. Refresh Token Server-Side Management

Use **SimpleJWT's blacklist/outstanding-token functionality**.

Do not create a custom `RefreshToken` database model unless a genuine requirement appears.

The previous NestJS approach of storing:

```text
token
userId
expiryDate
```

was valid, but SimpleJWT already provides appropriate infrastructure for this project.

Enable the necessary SimpleJWT blacklist application and use it for refresh-token revocation.

---

# 17. Token Lifetime

Use short-lived access tokens and longer-lived refresh tokens.

Reasonable starting point:

```text
Access token  → 5–15 minutes
Refresh token → several days
```

Exact values can be adjusted during implementation.

Avoid unnecessarily long-lived access tokens.

---

# 18. Token Refresh Flow

Normal flow:

```text
Browser
   │
   │ access cookie
   ▼
Django API
```

After access-token expiration:

```text
API request
   ↓
401
   ↓
POST /api/v1/auth/token/refresh/
   ↓
refresh cookie
   ↓
new access token
   ↓
retry original request
```

The frontend should handle this transparently where appropriate.

---

# 19. Logout

Logout should:

1. receive/identify the refresh token;
2. blacklist it through SimpleJWT;
3. clear authentication cookies.

Important:

A stateless access JWT that has already been issued cannot necessarily be revoked immediately. Its short lifetime limits the exposure.

---

# 20. CSRF

Because authentication uses cookies, CSRF protection must be configured correctly.

Do not disable CSRF to simplify development.

Configure:

- Django CSRF middleware;
- trusted origins;
- frontend/backend origins;
- CSRF token handling for state-changing requests.

Production cookies should use:

```text
Secure=True
```

Local HTTP development may require environment-specific configuration.

# 29. Query Optimization

```python

```

# 35. Celery + Redis

Implement the second bonus requirement using:

```text
Celery
+

```

Architecture:

```text
Django
   │
   │ enqueue task
   ▼
Redis
   │
   │ broker

   │
   ▼

```

Celery handles asynchronous task execution.

Redis acts as the broker.

They are separate components with separate responsibilities.

# 36. Email Notification

After successful event registration:

```text
POST /events/{id}/register/
        ↓
database transaction
        ↓
registration created
        ↓
enqueue Celery task
        ↓
return API response
```

The HTTP request should not wait for the email to be sent.

The Celery worker sends the notification asynchronously.

The email should contain useful information such as:

- event title;
- date;
- location;
- registration confirmation.

---

# 37. Celery Task Arguments

Pass primitive identifiers to Celery tasks.

Prefer:

```python
send_registration_email.delay(user_id, event_id)
```

over:

```python
send_registration_email.delay(user, event)
```

The worker can retrieve the required records from the database.

Do not pass Django model instances to Celery.

Retry logic can be added where genuinely useful, but do not build an elaborate retry system for this small application.

---

# 38. Transaction + Celery

Do not enqueue the email before the registration transaction is safely committed.

Prefer transaction hooks such as `transaction.on_commit()` when appropriate.

Desired sequence:

```text
DB commit
   ↓
enqueue email task
```

Avoid:

```text
enqueue email
   ↓
DB rollback
```

This prevents sending an email for a registration that ultimately does not exist.

---

# 39. Celery Beat

Do not use Celery Beat.

There are no periodic tasks in the requirements.

A Celery worker is sufficient.

---

# 40. Redis Caching

# 71. Final Rule for the Implementation Agent

When implementing something, prefer this order of reasoning:

1. **Does the original task require it?**
2. **Does it solve a real problem in this application?**
3. **Is there a standard Django/DRF solution?**
4. **Can it be implemented simply?**
5. **Only then consider adding an abstraction or dependency.**

Do not introduce a pattern merely because it is described as a "best practice."

The final project should be **small enough to understand quickly, but polished enough to look like a serious production-oriented implementation**.
