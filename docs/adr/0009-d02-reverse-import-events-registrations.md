# 0009 (D02). Допущен обратный импорт events → registrations

## Контекст

`interfaces.md` изначально описывал зависимости модулей однонаправленно: `registrations →
events → users`, без обратных импортов; план подразумевал, что `apps.events` ничего не знает о
существовании `apps.registrations`.

## Решение

`apps/events/views.py` импортирует `register_user_for_event` и `cancel_registration` из
`apps.registrations`, а `apps/events/filters.py` импортирует `EventRegistration` для фильтра
`registered`. Оба импорта из `events` в `registrations` разрешены и явно зафиксированы в
`interfaces.md` как единственные допустимые исключения из однонаправленности.

## Почему

Отвергнут вариант «сохранить строгую однонаправленность и вынести register/cancel в отдельный
роутинг под `apps.registrations`» — спецификация требует `register`/`cancel` именно как
`@action` на `EventViewSet` (запись — подресурс события, а не отдельный ресурс) и фильтр
`registered` именно на `EventFilter`, без отдельного эндпоинта под `/my-events`. Выполнить этот
контракт API и одновременно не импортировать `apps.registrations` из `apps.events` было
невозможно — это не выбор реализации исполнителя, а прямое следствие формы API, зафиксированной
спецификацией.

## Последствия

`apps.events` больше не полностью независим от `apps.registrations`: правило «зависимости идут в
одну сторону» в `interfaces.md` расширено, чтобы разрешить именно эти два места импорта, и любой
новый обратный импорт сверх них требует пересмотра этого решения, а не тихого добавления по
аналогии. Тестировать `apps.events` в полной изоляции (например, вырезав `apps.registrations` из
`INSTALLED_APPS`) больше нельзя.
